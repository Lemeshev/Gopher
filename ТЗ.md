## 0. Кратко о задаче

Заказчик получил HTML5/Canvas тамагочи-игру **Gopher Life** (папка `www/`),
обёрнутую в Android WebView (`android/`). От исполнителя требуется:

1. Довести игру до состояния «работает на телефоне», починив все известные баги.
2. Собрать **подписанный release APK** и положить его на рабочий стол как
   **`Gopher.apk`** (имя файла — требование заказчика, не «как получилось»).
3. Доказать работоспособность **независимыми ревьюерами**, а не словами.

Игра в репозитории уже есть. Ничего «с нуля» писать не нужно — нужно
**починить и доказать**.

## 1. ГЛАВНОЕ ПРАВИЛО ПРОЦЕССА (требование заказчика, дословно)

> «После КАЖДОЙ правки КАЖДЫЙ из 4 ревьюеров заново с нуля проверяют ВЕСЬ
> процесс. Только когда ВСЕ ревьюеры согласны — тогда двигаемся дальше.
> Когда ВСЁ сделано — все всё проверяют ещё раз. Исходя из всех условий задачи.»

### Как это исполнять буквально

1. **Любая правка** (одна строка, файл, конфиг, картинка) → **полный прогон
   всех ревьюеров с нуля** по всему проекту. Не «только изменённый файл»,
   не «это я уже проверял», не «правка косметическая».
2. **«С нуля»** = команды запускаются заново, весь набор проверок, по всему
   проекту, без опоры на память о прошлом прогоне.
3. **Пока есть хоть один красный пункт у любого ревьюера — следующую правку
   не начинать.** Сначала зелёный прогон, потом следующий шаг.
4. **Вердикт выносится по ПОЛНОМУ списку условий** (раздел 3), а не по тому,
   что исполнитель вспомнил. Не записано в условия/проверку — значит для
   приёмки не существует.
5. **Финальный прогон.** Когда исполнитель считает, что всё сделано — все
   ревьюеры прогоняются **ещё раз** с нуля, по всем условиям, и только тогда
   результат объявляется готовым.
6. **Отчёт только фактами.** Каждое «сделано» подтверждается выводом команды,
   скриншотом или md5. Чего проверить не удалось — так и писать
   «не проверено» со причиной, а не «работает».

### Про количество ревьюеров (важно, не путаться)

Заказчик требует **4 независимых ревьюера**. В проекте их сейчас **5**:
4 «логических» + 5-й **рендер** (`tools/render-check.js`), который добавлен
принудительно, потому что ревьюеры 1–4 работают на **заглушке canvas** и по
устройству не могут увидеть пиксели (см. раздел 5, причина №5).
Правило из п. 1–6 распространяется на **всех пятерых**:
после каждой правки — полный прогон `npm run verify`, ожидаемый итог
`провалено 0`. Меньше пяти согласных ревьюеров — «дальше не двигаемся».

## 4. Команды и обязательный цикл после КАЖДОЙ правки

```bash
cd ~/gopher/gopher-life

# 1) Собрать заново и положить на рабочий стол (внутри: sync www→assets, gradle, копия)
npm run apk:desktop        # ~1 мин

# 2) Полный прогон ВСЕХ ревьюеров с нуля (главное правило из раздела 1)
npm run verify             # ~2–3 мин; ожидается "провалено 0", код выхода 0

# 3) Снять реальные кадры всех сцен (это уже внутри verify, отдельно — для глаз)
npm run render -- --shots=preview/screens
```

**Почему именно такой порядок и почему его нельзя менять:**

- Ревьюер 4/5 сверяет **содержимое APK с исходниками**. Если правка сделана в
  `www/`, но APK не пересобран — ревьюер 4 падает на «JS внутри APK устарели».
  Это и есть защита от бага «чёрный экран» (раздел 5, причина №1).
  Поэтому: **сначала сборка, потом проверка.**
- `npm run build` сам вызывает `tools/sync-www.js`, который копирует `www/` в
  `android/app/src/main/assets/www/` и удаляет оттуда устаревшие файлы.
  Руками копировать нельзя — забудется.
- Ревьюер 5/5 требует установленный **Google Chrome** (путь можно задать в
  `CHROME_BIN`). Он запускает игру в реальном браузере и читает пиксели канваса.
  Без него «зелёный» прогон недействителен: именно он ловит пустой экран.

**Чего этот цикл НЕ проверяет (и что обязан сделать исполнитель руками):**

- наложение и обрезку элементов интерфейса — **только глазами** по
  `preview/screens/*.png` (раздел 8);
- реальный запуск на Android-устройстве — эмулятора/устройства на машине нет.

## 5. Почему исполнитель обсирается — разбор без отговорок

Заказчик прав: это не первый провал. Ниже — что именно ломалось, почему это
проходило сквозь «зелёные» проверки и какая системная причина за этим стоит.
**Прочитать до начала работы: это карта уже заминированных мест.**

### 5.1 Факты провалов

| № | Что случилось | Почему проверки это пропустили |
|---|---|---|
| 1 | **Чёрный экран** в собранном APK | APK собирался из `android/.../assets/www/`, а правки шли в `www/`. Копия была устаревшей: старый `index.html` без `new Game().init()`. Проверок «APK == исходники» не было вообще; синхронизация была ручной (`cp`), и её забыли. |
| 2 | **Не работали кнопки вообще нигде** | `createButton()` в `helpers.js` возвращал `{x,y,w,h}` **без поля `text`**, а все сцены проверяли `btn.text`. Проверок кликов не существовало — тесты «рисовали» и радовались. |
| 3 | **Пустая иконка на Android 5–7** | Иконка была VectorDrawable; на API 21–25 system launcher vector-иконки **не рендерит**. Проверялось «файл существует и это vector», а не «работает на целевых API». Итог: на половине устройств под иконкой была пустота. |
| 4 | **Имя файла не то** | Требовалось `Gopher.apk`, отдавалось `GopherLife.apk`. Требование было известно, но **не записано ни в одну проверку** → для ревьюеров не существовало. |
| 5 | **Верстка сломана, а «54/54 пройдено»** | Ревьюеры 1–4 работают на **заглушке canvas**: код исполняется, исключений нет — «успех». Что нарисовалось — не видно. Так жили: обрезанные кнопки на «Доме», обрезанный ряд товаров и кнопка «Назад» поверх карточек в «Магазине», бейдж цены поверх названия на «Карте», сырое `morning` вместо «Утро». |
| 6 | **Ложный диагноз от самого исполнителя** | Первый прогон реального рендера выдал «чёрный экран в игре». Оказалось — баг **моего стенда**: `var f = g.loop; f()` теряет `this`. То есть я почти отдал заказчику выдуманную проблему вместо своей. |

### 5.2 Системные причины (главное)

1. **Критерии приёмки не были зафиксированы письменно.** Я проверял то, что сам
   придумал проверять. Всё, что не превращено в проверку или в пункт ТЗ, для
   приёмки **не существует** — и проваливается в продакшн. Именно поэтому этот
   файл обязателен.
2. **Проверка логики подменяла проверку результата.** «Код выполнился без
   ошибок» ≠ «на экране то, что нужно». Тесты на заглушке canvas не видят
   пикселей по своей природе.
3. **Не было правила «после каждой правки — полный прогон с нуля».** Я гонял
   частичные проверки (только изменённый файл) и делал вывод «всё цело»,
   пропуская регрессии в других местах.
4. **Проверки писались под уже найденный баг, а не под требование.** Такие
   тесты — регресс-защита, они по определению не ловят новые классы дефектов.
   Пример: после починки иконки проверяли наличие файла, а не работу на API 21.
5. **Плохие новости откладывались.** «На реальном устройстве не проверялось»
   всплывало в конце мелким шрифтом вместо того, чтобы быть заявленным сразу.
   Непроверенное должно объявляться **в момент обнаружения**, а не при сдаче.
6. **«Готово» объявлялось без доказательств и без согласия всех ревьюеров.**
   Слова «исправлено» без вывода команды/скриншота/md5 не значат ничего.

### 5.3 Как это лечится (правила для преемника, обязательные)

- Сначала **проверка**, потом код. Нет проверки для требования — требование
  не выполнено, даже если код написан.
- После **любой** правки — полный прогон `npm run verify` (раздел 1 и 4).
- Артефакт доказывается артефактом: `npm run verify` (провалено 0) + свежие PNG
  из `preview/screens/` + `md5 ~/Desktop/Gopher.apk`.
- Вопросы «как правильно по требованию заказчика» задаются **до** работы,
  а не после сдачи (пример: `android:label`).
- Сомневаешься, что что-то работает — считай, что не работает, пока не показал.

## 8. Слабые места автоматики — НЕ считать закрытым

1. **Наложение и обрезка элементов не детектится автоматикой.** Ревьюер 5/5
   видит только «кадр не пустой». Поэтому после каждой правки вёрстки —
   **обязательный ручной просмотр `preview/screens/*.png`**.
   Хочешь закрыть и это — нужно писать детектор пересечений (считать занятые
   области через `measureText` в сцене и падать при пересечении). Это отдельная
   задача, а не «и так видно».
2. **Проверяется только один размер экрана** (headless-окно 390×844, канвас
   ~500×757). Маленькие экраны, планшеты, вырезы и системные панели не покрыты.
3. **Ревьюер 5/5 требует Google Chrome** и идёт 1–3 минуты; при загруженной
   машине Chrome иногда не отвечает — на этот случай встроено 3 попытки
   (ложный провал безопаснее ложного успеха).
4. **Реальный WebView и устройство не тестируются**, только Chrome. Отличия
   возможны: звук, `localStorage`, поведение fullscreen, системные панели.
5. **Звук замокан** (`AudioSys` подменяется в стенде) — аудио не проверяется.
6. **Долгие таймеры** (автосохранение, старение питомца) искусственно не
   прокручиваются.

## 9. Пошаговый цикл для преемника

1. Прочитать этот файл **целиком** (особенно разделы 1 и 5).
2. Зафиксировать исходное состояние:
   ```bash
   npm run apk:desktop && npm run verify
   ```
   Записать фактические цифры и код выхода.
3. Открыть глазами все PNG из `preview/screens/` и составить список визуальных
   дефектов (обрезано / наложено / нечитаемо).
4. Любое требование, у которого нет проверки, — **сначала** превратить в проверку
   в `tools/verify.js` (или в новый инструмент), и только потом править код.
5. Вносить правки **по одной**.
6. **После каждой правки** (правило заказчика, раздел 1):
   ```bash
   npm run apk:desktop && npm run verify       # все ревьюеры, с нуля
   npm run render -- --shots=preview/screens   # свежие кадры
   ```
   плюс просмотр PNG глазами. Есть красный пункт — дальше не идти, чинить.
7. Когда всё зелёное и глазами чисто — **финальный полный прогон заново**.
8. Отчёт заказчику строго по формату из раздела 11. Всё, что не проверено,
   перечислить явно (разделы 3.8 и 8).
9. Отдельно закрыть открытые вопросы из раздела 7.
